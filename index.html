Memport — sample memory move

Carry what your agents know between tools. Claude Code, Codex, and Cursor each store memory differently — project files, rule directories, generated summaries — so switching tools today means starting from scratch. Memport converts that memory into one open bundle format (memport/1: a JSON manifest with SHA-256 hashes plus one markdown file per item) and renders it back into any supported tool. This page walks through a genuine run of the Memport CLI — not a mockup. Every command and output below is real output from a local demo run.

Sample data only. All projects, rules, and identities are demo fixtures. Honest limits: exported items are context, not enforcement — the target tool can still ignore them. Codex import is summaries-only (its memory store is vendor-generated state). Cursor carries rules only (its Memories feature was removed in 2.1.x). Conflicts are never resolved by meaning — merges pick a winner by status, origin, and recency, and preserve the loser. Mutating commands default to plan mode and write nothing until you pass --apply.

2. Bundle: Claude memory into one portable bundle

Four project rules become four items with stable ULID identities. The bundle is a directory you can copy, commit, or send — and validate checks every item hash before anything is trusted.

3. Apply: the same bundle lands in Codex

Apply renders the bundle into Codex's AGENTS.md inside a delimited section, one provenance line per item, so the import is auditable and re-applying is a clean noop. The plan names every item and its losses before anything is written — and warns plainly that per-item ids do not survive re-import of the rendered file.

$ memport apply --bundle ./demo/bundle-claude --to codex --scope project --project ./demo/codex-target --apply
Apply plan → ./demo/codex-target/AGENTS.md
  action: create
  backup: none needed (target does not exist yet)
  rendered: 4 active item(s); skipped: 0 superseded, 0 disputed
    - .claude/CLAUDE.md (01M5V9CYGHFQACFHXAFY901PV3)
    - CLAUDE.md (project) (01M5V9CYGHYX9R882AHB04JV5W)
    - deploy (01M5V9CYGJD0JP0HY9J5WVFG75)
    - testing (01M5V9CYGKFMG1ESWM9103KTM1)
  losses:
  - rendered-as-instructions: 4 (e.g. .claude/CLAUDE.md, CLAUDE.md (project), deploy)
  - claude-paths-scoping-lost: 1 (e.g. testing)
  warning: Identity loss on re-import: per-item ids do not survive re-import of the rendered AGENTS.md section — re-import mints new ids unless the title-match idempotence rule matches (same source tool, source path, normalized title). Keep the bundle as the source of truth.

5. Merge: an edited copy supersedes, nothing is deleted

Re-bundling the same project after an edit reuses the same ids, so the old and new bundles share one item with two bodies. Merge picks the newer version as the winner — and preserves the loser verbatim in merge-report.md inside the output bundle. The merged bundle validates cleanly.

$ memport bundle --from claude --scope project --project ./demo/project-v1 --out ./demo/bundle-a --apply
Bundle plan: claude (project) → ./demo/bundle-a
  collected: 4 item(s) (rule=4)
  reused ids: 4, new: 0, kept from existing bundle: 4
  warning: no Claude auto-memory directory at ./fixtures/claude-home/projects/-tmp-memport-demo-project-v1/memory (skipped)
  import losses:
  (none)
  WROTE bundle to ./demo/bundle-a (4 items).
$ memport merge ./demo/bundle-a-v1 ./demo/bundle-a --out ./demo/merged --apply

Run it yourself

npm install && npm run build
node dist/cli.js scan --project <dir>
node dist/cli.js bundle --from claude --scope project --project <dir> --out <bundle> --apply
node dist/cli.js apply --bundle <bundle> --to codex --scope project --project <dir> --apply
node dist/cli.js convert --from claude --to cursor --scope project --project <dir> --out <bundle> --apply
node dist/cli.js merge <bundleA> <bundleB> --out <merged> --apply
node dist/cli.js validate <bundle>
